# 在多线程中，如何管理资源

在多线程网络服务器（如 `TcpServer`）中，`Connection` 对象在主线程创建，并在 IO 线程和业务工作线程中流转和调用。如果客户端中途断开连接，会导致对象被释放；此时如果业务线程依然持有着该对象的常规（Raw）指针，程序将会出现严重问题。因此，常规指针无法满足多线程下的资源生命周期管理，必须采用智能指针。

1. **“悬垂指针 / 内存踩踏”**：
   * 如果 `Connection` 已经被 IO 线程释放（`delete`），但业务线程还拿着它的原指针去访问，这会导致**程序崩溃（Core Dump）**或数据错乱，这叫“悬垂指针”。
   * 相反，如果大家都不敢 `delete`（因为不知道业务线程是否还在用），最终导致对象永远不被释放，这是**内存泄漏（Memory Leak）**。
2. **核心痛点**：多线程环境下，**资源的析构时机是不可预测的**。你无法在主线程或 IO 线程中武断地 `delete` 资源，因为你不知道工作线程是否正在处理它的数据。

---

### 二、 为什么必须使用智能指针？（必要性）

在多线程中保证资源有效，本质上是解决**“谁来负责销毁对象”**以及**“什么时候销毁最安全”**的问题。

智能指针（主要是 `std::shared_ptr` 和 `std::weak_ptr`）的必要性体现在：

1. **自动的生命周期管理（引用计数）**：
   `std::shared_ptr` 内部维护了一个原子操作的“引用计数”。无论对象**被传递到多少个线程**，只要还有至少一个 `shared_ptr` 指向它（引用计数 > 0），它就不会被销毁。当最后一个使用者离开作用域时，对象才会被安全销毁。
2. **解决“多线程下的析构竞态”**：
   无需再手动 `delete`。IO 线程发现客户端断开时，只需销毁自己手里的 `shared_ptr`；如果此时业务线程还在处理该连接的任务，业务线程手里的 `shared_ptr` 会保住这个连接对象不死。等业务处理完，`Connection` 才会真正析构。
3. **安全的存活检测（`weak_ptr`）**：
   有时候业务线程只想知道“这个连接还活着吗？如果活着就发数据，死了就算了”。此时用 `std::weak_ptr` 探针，既不会延长对象的寿命，又能安全地检测对象是否已经被销毁，避免对已断开的连接进行无效处理。

### 三、 改为智能指针

为了方便，直接：

```cpp
#include<memory>
class Connection;
using spConnection = std::shared_ptr<Connection>;
```

先定义，才能换个别名，不然太长

然后将：
`Connecion* -> spConnection`

其中的this指针也需要替换

先将Connection类继承一个模板类，然后替换一下this指针即可，如下：
```cpp
class Connection:public std::enable_shared_from_this<Connection>
{
// 将this 替换为： shared_from_this() 即可
}
```

另外删除delete conn的所有代码，因为不需要手动销毁

修改的时候，从Connection层逐渐向上层修改，那么这个野指针的问题就得到了解决

### 四、 进一步完善

“如果 TCP 连接断开（read 返回 0 或触发 EPOLLERR/EPOLLHUP），为了防止 Epoll 产生无效的事件循环（Busy Loop）以及文件描述符泄露，我们必须**第一时间调用 epoll_ctl(EPOLL_CTL_DEL) 将该 Channel 从 Epoll 树上删除，取消所有事件的监听，随后再将其从服务器容器中移除，并安全地关闭 Socket 及释放相应内存。**”



在你目前的架构中，完整的正常关闭流程应该是这样的：

1. Connection::onmessage() 发现 nread == 0。
2. 调用 Connection::closecallback()。
3. **关键步骤：** 在 Channel 类中调用类似 disableall() 的方法，取消对 EPOLLIN 和 EPOLLOUT 的关注，并调用 epoll_ctl 的 EPOLL_CTL_DEL 把该 fd 从 Epoll 树上**彻底摘除**。
4. 执行回调来到 TcpServer::closeconnection()。
5. 将此连接从 TcpServer 的 conns_ Map 中 erase 掉。
6. delete conn; 触发 Connection 的析构函数。
7. Connection 析构时，delete clientchannel_ 和 delete clientsock_，在 Socket 的析构函数里真正执行 ::close(fd) 关闭底层套接字。



“在多线程 Reactor 网络模型中，**TCP 连接的断开必须驱动两件事**：

1. **在底层**，必须立即取消该 Channel 的所有关注事件，并将其从 Epoll 树上注销，最后关闭 Socket 释放资源。
2. **在上层**，必须通过智能指针（如 weak_ptr 的提升检测）来确保跨线程生命周期的安全，防止工作线程向已经释放的连接对象调用 send() 而引发段错误。”

下面修改Connection类，确保：TCP连接断开后，就不发送数据

```cpp
// Connection 类
std::atomic_bool disconnect_;   // 客户端连接是否已断开，如果已断开，则设置为true
// 在IO线程中，会改变其值
// 在工作线程中，会判断其值，因此用原子类型，确保同步，正确
```

当断开连接的时候，将该变量设置为true

在send()函数里，判断该变量，如果返回的是true,那就return，不再发送事件
